## 风险与注意事项

- **`pay` 兼容性**：请求体从「无」变「可选对象」，必须保证空 body 仍可用（旧前端、E2E 旧用例）。改动后先跑 `test_records.py` 与 `test_operations.py` 确认无回归。
- **同事务要求**：`pay` 的日期推进与流水生成必须同事务，否则校验失败会留下「日期走了但没记账」的脏状态。用 `db.rollback()` 或先校验后写的方式保证。
- **余额性能**：余额用 SQL 聚合（`func.sum` + `case`），不要拉全表到 Python 再累加。
- **`expense_id` 的 `ondelete=SET NULL` 依赖 `PRAGMA foreign_keys=ON`**：现有 `database.py` 已开启，需在测试里断言该行为而非假设。
- **旧导出兼容**：导入旧导出会把记账数据清空（「整体替换」语义），必须在 `api.md` 与 `HANDOFF.md` 写明，避免用户误以为数据丢失。
- **不静默截断**：`entries` 超 `limit` 返回 422 而不是截断，符合项目「显式优先」的既有风格。
- **商户字典化的减负设计不能省**（设计文档里列了四条）：录入即可新建、前缀匹配、合并、归档。若只做字典表而不做「输入即新建」，记账会退化成「先去维护字典再记账」，实际不可用。
- **商户名称归一**：`POST`/`PATCH` 一律先 `strip()` 再判重，避免出现「老张面馆」与「老张面馆 」两条；唯一约束必须忽略大小写。测试要覆盖这条。
- **商户合并是同事务的改挂 + 删除**：不要用 `DELETE` 级联，也不要把来源留成空壳；合并后残留的流水引用必须为 0。
- **SQLite 不能给已有表加带外键的列**：`expenses` 的 `account_id`/`category_id`/`payee_id` 因此不带 `REFERENCES`——Alembic 只能靠重建表，而重建 `expenses` 会一并重建它那条匿名 `user_id` 外键，SQLite 方言直接抛 `Constraint must have a name`。引用完整性由接口层的 409 检查承担；`ledger_entries.expense_id` 的外键保留在新表定义里。
- **裸外键的校验归一化**：`ledger_entries` 是首个带「未声明 ON DELETE」外键的表，`cli.validate_database` 必须按 `fk.ondelete or "NO ACTION"` 比对，否则备份恢复会以「ownership constraint missing」拒绝合法备份。
- **diff 控制**：本批不迁移 `domain.ts` 的 `money`/`monthlyCost`/`expenseSummary`，也不引入 eslint/prettier，保持一次可审查的改动范围。
