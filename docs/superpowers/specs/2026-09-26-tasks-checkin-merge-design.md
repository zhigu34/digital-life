# 待办与打卡合并为「任务」设计（用户已确认范围，2026-09-26）

状态：**已实现并合入 `main`（2026-09-26，`bdf385a`）**。第 0 节是用户确认的 5 项决策，第 12 节是另外 4 项细节（用户授权按默认建议执行）。实施分支 `codex/tasks-checkin-merge`，前端目录落地为 `features/tasks/`（`app/groups/` 对应后端），验证结果见 `docs/HANDOFF.md`。

目标：把现在的「待办清单」和「打卡」合并成一个「任务」页，只保留两种**互不相通**的任务形态：

1. **一次性待办**（现有 `tasks`，独立选项，不可与长期任务互相转换）。
2. **长期任务**：以「分组」承载，分组内可同时放多个打卡项，每项有自己的周期（每天 / 每周 / 每月）。每周、每月都是**周期内完成即可，不设固定日期**：本周做过一次就算本周达标，本月做过一次就算本月达标。

合并的动机（代码事实，非设想）：现在同一件事要用户自己决定记在哪边 —— 想每天做又想要优先级/备注就得建两条记录；打完卡看不到"今天别的该做的事"，待办里也看不到"坚持了几天"。`tasks` 没有完成历史（`backend/app/models.py:47-54` 只有 `status`），`checkins` 没有优先级/一次性形态，两套模型各自缺一半。

## 1. 非目标

- **不做"每周 N 次"（N>1）配额**。本设计的周期达标条件是"周期内 ≥1 次"；一个周期内多次完成会被计数展示，但不改变达标门槛。把门槛参数化是后续扩展（加一列 `target_count` 即可）。
- **不物化周期行**。不为每个周期预生成数据库记录、不加后台定时任务：周期状态由规则实时派生，完成情况来自完成记录表。理由与记账"余额派生不落库"、维护"`next_due` 由最新完成日派生"（`backend/app/maintenance.py:48-70`）一致 —— 一旦物化，就要处理"生成了没做""改了周期旧行怎么办"两类不一致。
- 不改周期维护（`maintenance`）与「在做」（`projects`）的语义（第 3 节）。
- 不做站内提醒/推送。
- 不再有"计划日"概念，因此也没有"计划外补录"这类分支：长期任务任意一天都可以打卡。

## 3. 概念边界（三类东西不能互相替代）

| 概念 | 形态 | 完成记录 | 日期怎么走 |
|---|---|---|---|
| **一次性待办** | 单条任务，有状态/到期日/优先级 | 无（只有 `completed_on` 一个"哪天做完"） | 做完即 `done`，不重复 |
| **长期任务**（本设计） | 分组 + 分组内打卡项（每项一个周期） | 有，按日历日一条 | **不推进**：周期是固定的格子，"本周没打卡"永远留着 |
| **周期维护** `maintenance` | 单条事项 + 完成历史 | 有，按实际完成日 | 按**最新实际完成日**顺延，补录不倒退（`maintenance.py:55-70`） |
| **在做** `projects` | 单条，纯状态 | 无 | 无周期概念 |

长期任务与周期维护很容易被混为一谈（都有"完成记录"和"后来呢"），但**顺延规则相反**：维护关心"下次什么时候该做"，长期任务关心"这个周期有没有做过"。把长期任务做成顺延就丢掉了"哪一周漏了"这个唯一的信息；把维护做成周期格子就丢掉了"按实际完成日算下次"的语义。这条边界与 AGENTS.md 中「周期维护与固定账单语义不同」是同一类约束。

## 4. 数据模型（Alembic `0011`）

### 4.1 `tasks`（一次性待办）只加一列

| 字段 | 类型 | 规则 |
|---|---|---|
| `completed_on` | Date nullable | `status` 变 `done` 时由服务端写用户时区今天；退回 `todo` 时清空。用于日历与今日概览显示"哪天做完的" |

**不加 `kind`、不加周期字段**。一次性与长期任务是两种数据集，"独立选项、不可互转"用两张表最诚实地表达；共表会让 `status`/`due_date` 与周期字段各自半空，还要在 PATCH 里防守 `kind` 互转。

### 4.2 `task_groups`（长期任务 = 一个分组）

| 字段 | 类型 | 规则 |
|---|---|---|
| id / user_id | | `Owned` 基类，归属由服务端会话决定 |
| title | String(120) | 1–120；即用户看到的"这个长期任务"的名字（如"健身计划"） |
| notes | Text | ≤4000，默认 `''` |
| archived | Boolean | 归档后整个分组不再出现在今日待做、不能打卡；历史保留 |
| archived_on | Date nullable | 归档生效日，**分组展示的截止日**；未归档为 null。`archived=false` 时清空 |
| created_at | DateTime | 服务器时间 |

### 4.3 `task_group_items`（分组内的打卡项）

| 字段 | 类型 | 规则 |
|---|---|---|
| id | 主键 | |
| group_id | FK `task_groups.id` ondelete CASCADE，index | 归属由分组确定 |
| title | String(120) | 1–120（如"跑步 30 分钟"） |
| repeat_unit | String(8) | `day` / `week` / `month`，必填 |
| start_date | Date | 从哪个周期开始期待；默认创建当天（用户时区）。早于此日不参与投影 |
| created_at | DateTime | 服务器时间 |

**没有 `repeat_on`、没有 `end_date`、没有月末锚定** —— 周期内完成即可，不存在"哪一天做"。单项停用（`archived`）暂不做：要停就归档整个分组，或删掉该项（用户明确要求不为合并引入多余元素，字段能省就省）。

### 4.4 `task_completions`（打卡记录，挂在项上）

| 字段 | 类型 | 规则 |
|---|---|---|
| id | 主键 | |
| item_id | FK `task_group_items.id` ondelete CASCADE，index | |
| completed_on | Date | 完成日期（用户时区日历日） |
| note | Text | 当天备注 ≤4000，默认 `''` |
| created_at | DateTime | 服务器时间 |
| — | `UNIQUE(item_id, completed_on)` | 同日唯一，DB 兜底并发；重复写入 409（沿用 `checkins.py:181-185` 的处理方式） |

一个周期内允许多条（每天一次），达标只看"有没有"。

### 4.5 为什么不做自引用单表

曾考虑 `tasks` 自引用 `parent_id`（分组是 `recurring` 行、打卡项是子行）。放弃的原因：一次性待办的 `status/due_date/priority` 与打卡项的 `repeat_unit` 会各自半空，`kind` 变成三态，通用集合的 PATCH 校验与导出格式都要为三种形态写分支。三张专用表的写入路径更窄、校验更直白。

## 5. 周期口径（本设计的核心）

### 5.1 周期容器

以**用户时区**（`app/timezones.py` 的 `user_today()` 是唯一归属地）划分：

| `repeat_unit` | 周期 | 起止 |
|---|---|---|
| `day` | 日历日 | 当天 00:00–24:00 |
| `week` | 自然周 | 周一 00:00 – 周日 24:00（与 `frontend/src/calendar.ts:32-57` 的 Monday-first 网格一致） |
| `month` | 自然月 | 当月 1 日 – 月末 |

周期标识：`day` → `YYYY-MM-DD`；`week` → `YYYY-Www`（ISO 周，跨年周按 ISO 归属）；`month` → `YYYY-MM`。

### 5.2 周期状态只有三态

| 状态 | 条件 |
|---|---|
| `done` 已达标 | 该周期内 ≥1 条完成记录 |
| `missed` 未达标 | 周期已结束 且 0 条记录 |
| `pending` 进行中 | 当前周期 且 0 条记录（**倒数第二个周期起才算 `missed`，当前周期永远不算漏做**） |

周期早于 `start_date`、或晚于 `archived_on`（分组归档日）→ 不计入投影（既不是 `missed` 也不是 `pending`，展示为空白/未开始）。

展示上"已完成/未完成"依然清晰，只是**粒度跟着周期走**：每日项看天，每周项看周，每月项看月；周期内多次完成显示次数（如 `×2`）。

### 5.3 指标

| 指标 | 定义 |
|---|---|
| 本期次数 | 当前周期内的完成条数（每日项即"今天几次"，通常 0/1） |
| 连续达标 | 从上一个已结束周期往前数，连续 `done` 的周期个数。**当前周期未达标不算断**（沿用 `frontend/src/checkin.ts:9-23` 既有规则：今天没做不断、昨天也缺才归零） |
| 达标率 | 近 N 个**已结束**周期中 `done` 的比例（每日 N=30，每周 N=8，每月 N=6）。分母只含已结束周期，不含未来、不含 `start_date` 之前、不含归档之后 |
| 分组本期进度 | 分组内各项的当前周期状态汇总 `x/y 项已达标`，排序把未达标项排前面 |

"分母只含已结束周期"这条很关键：周一早上看每周项不会显示 0/1 未达标，而是"本周进行中"。

### 5.4 服务端 / 前端分工

- `GET /api/groups` 返回**原始事实**：分组与项字段 + 每项最近 400 天完成日期（`recent_days`，沿用 `DAYS_WINDOW`）+ `total_count`。
- 周期归属、三态、连续达标、达标率由前端纯函数 `features/tasks/periods.ts` 派生（沿用 `checkin.ts` 先例）：周/月格子需要渲染任意历史区间，做成服务端聚合就要为每个视图设计参数，且纯函数可单测、无网络往返。**完成记录优先于 `start_date`**：补记在开始日期之前的日期照旧算达标并计入连续，`start_date`/`archived_on` 只决定空周期算不算漏做。
- **一旦引入跨任务的汇总**（如今日概览"共 5 项待做"、`/api/stats` 里的完成率）就由服务端算，前端不得自行加总 —— 遵守 AGENTS.md「统计口径以 `/api/stats` 为唯一真源」。

### 5.5 ISO 周边界（最容易写错的地方）

- 周起点固定周一；`week` 键用 ISO 周号，1 月 1 日可能属于上一年的第 52/53 周（如 2027-01-01 属于 2026-W53）。
- 跨年周在"最近 8 周"里必须连续不断档：派生函数按"今天所在周的周一"每次减 7 天生成，而不是按周号字符串拼。
- 单测要覆盖：跨年周、闰年 2 月、月长 28/29/30/31、以及"周内任意一天完成都算本周达标"。

## 6. 行为规则

1. **打卡**：`on` 缺省为用户时区今天；`on > user_today(tz)` → 422；同一项同一天重复 → 409；撤销无记录 → 404（全部沿用打卡现有语义，只是归属从"打卡项"换成"分组内的项"）。
2. **周期内多次完成**：允许，计次数，不改变达标门槛（`×2` 徽标展示）。
3. **归档分组**：`archived=true` 时写 `archived_on=今天`；此后不再进入今日待做、不能打卡（400，与 `checkins.py:168-169` 一致），历史格子照旧显示到归档日为止；恢复归档清空 `archived_on`。
4. **删除**：删分组级联删项与完成记录（DB 外键）；删单个项级联删该项的完成记录。确认文案必须写明"及全部打卡记录，删除后无法恢复"。
5. **一次性待办**：`PATCH {status:'done'}` 写 `completed_on=今天`，`PATCH {status:'todo'}` 清空。现有 `CollectionView` 的勾选按钮与 `TodayView` 的 `complete` 事件（`App.vue:71`）不需要改。
6. **不可互转**：`/api/tasks` 的请求体 `extra="forbid"` 会直接 422 掉 `repeat_unit` 之类的字段（沿用 `schemas.py:47-49` 的 `Payload` 配置）；UI 上也不提供"改成长期任务"。想换形态 = 新建 + 删除/归档旧的。
7. **没有"顺延"**：长期任务完成后不推进任何日期，周期格子照旧。**没有"开始日期之前补卡"的限制**：`start_date` 只影响投影是否期待，不影响能否补录历史（用户可以在项创建前的某天补一条，此时该周期算 `done`）。
8. **时区**：所有"今天/本周/本月"按用户时区判定；用户改时区后完成日期不变，只有周期归属与"当前周期"随之变化。

## 7. API 契约（新域包 `app/groups/`）

一次性待办沿用 `records.py` 的通用集合，只加 `completed_on` 字段。长期任务是新域包，与 `app/ledger`、`app/shows`、`app/bookmarks` 同结构（`router.py` / `service.py` / `schemas.py`）：

| 端点 | 行为 |
|---|---|
| `GET /api/groups` | 分组列表，含每个项（id/title/repeat_unit/start_date/recent_days/total_count）。**单条 SQL 按 `item_id IN (...)` 取完成窗口再内存分组，禁止 N+1** |
| `POST /api/groups` | 创建分组，可同时带 `items: [{title, repeat_unit}]`（前端一步创建"分组 + 首个打卡项"，单项目组不额外费事）；空 `items` → 422 |
| `GET/PATCH/DELETE /api/groups/{id}` | 分组读写；DELETE 级联删项与记录 |
| `POST /api/groups/{gid}/items` | 新增打卡项 |
| `PATCH/DELETE /api/groups/{gid}/items/{iid}` | 改标题/周期/开始日期；删除该项及其记录 |
| `POST /api/groups/{gid}/items/{iid}/complete` | `{on?, note?}` → 201 返回更新后的项；未来 422、同日 409、分组已归档 400 |
| `DELETE /api/groups/{gid}/items/{iid}/complete/{on}` | 204；无记录 404 |
| `GET /api/groups/{gid}/items/{iid}/completions?start=&end=` | 完成明细（含备注），跨度 ≤366 天；用于周期格子的"这周哪天打的卡"和历史列表 |

二级归属全部 404（分组不是自己的 / 项不属于该分组），不泄露存在性。

导出 / 导入：

- `/api/export` 的 `tasks` 多一个 `completed_on`；新增 `task_groups`、`task_group_items`、`task_completions` 三个键；**移除 `checkins` / `checkin_logs`**。
- `/api/import` **必须继续接受旧导出**：见到 `checkins` + `checkin_logs` 时，转成"一个分组 + 一个 `repeat_unit='day'` 的项 + 完成记录"，与 `tasks` 键合并；校验失败整体回滚（沿用 `docs/contracts/api.md:52` 的既有约束，不许出现"被拒的导入清空数据"这类 bug）。
- CLI 恢复：`SCHEMA_REVISION` 升 `0011`，恢复校验同步（AGENTS.md 明示"模型/迁移版本变化时同步审视 CLI 恢复"）。旧备份（`0005` 结构）走既有路径：旧代码恢复 → 向前迁移。

### 8.2 卡片长什么样（文案是人话）

- 分组卡片标题：`健身计划`；副标题：`本周 2/3 项达标`。

## 9. 迁移与兼容（Alembic `0011`）

1. `ALTER TABLE tasks ADD COLUMN completed_on DATE`（SQLite 可空列，无需默认值）。
2. 建 `task_groups`、`task_group_items`、`task_completions`（含 `UNIQUE(item_id, completed_on)`）。
3. **数据搬迁**（Python 循环，用 `users.timezone` 把 `created_at` 换算成日历日）：每条 `checkins` → 一个 `task_groups` 行（`title`/`notes` 原样、`archived = not active`、`archived_on = null`）+ 一个 `task_group_items` 行（`repeat_unit='day'`、`title` 取分组标题、`start_date = 该任务最早的完成记录日期，无记录则 created 换算日`）。
   **用"最早完成日"而不是"创建日"作 `start_date`**，是为了不让历史凭空长出"未达标"的周/天（打卡项目创建后隔天才打卡是常态）。旧数据是每日项，`start_date` 只影响每日格子的起始位置。
4. `checkin_logs` → `task_completions`（按第 3 步的 id 映射表）。
5. `DROP TABLE checkin_logs` → `DROP TABLE checkins`（顺序不能反，先删子表）。安全性依赖 `deploy` 迁移前的一致性备份（AGENTS.md 已保证），迁移本身在同一事务内完成。
6. `downgrade()`：还原结构（删新表、建回 `checkins`/`checkin_logs`、删 `tasks.completed_on`）并按 3/4 反向映射尽力回迁数据；**明确它是"尽力而为"**，生产回退走预迁移备份 + 停服恢复。

迁移测试：构造 `0005` 结构 + 双账号打卡数据 → 升 `0011` → 断言分组数/项数/完成记录数/最晚完成日期不变、"单项目组"的 `repeat_unit='day'`、`start_date` 不晚于最早完成日、账号不串号；旧导出（`checkins` 键）导入后能往返。

## 13. 风险与权衡

- **周期内完成的语义边界**：每周项"周三已达标、周日又打了一次"计 `×2` 但门槛不变；用户若预期"每周固定要做满 N 次"，需要 P4 的 `target_count`。文案要把"本周内完成即可"说清。
- **改周期会重算历史投影**：把某项从 `每天` 改成 `每周`，历史的周/天格子会按新周期重新归类（完成记录本身不变）。缓解：保存前提示一次"修改周期会改变历史格子的统计方式"；不做周期版本化。
- **周/月格子的历史回看深度**：列表只带 400 天窗口，更早的周期靠 `GET .../completions?start=&end=`（UI 上是明细弹窗里的日期选择）。
- **两张表两套形态**：一次性待办与长期任务无法互转是刻意的，但用户可能先建错形态。缓解：创建入口明确分成两个按钮 + 文案说明；不做转换按钮（用户已明确不可互转）。
- **迁移不可逆性**：`downgrade` 只尽力还原；生产回退依赖 `deploy` 的预迁移备份与"停服 + CLI 恢复"流程。
- **时区改动**：改时区会让周期归属与"当前周期"平移，完成日期不动；文案保持"以你的时区计算"（今日概览已有同类说明）。
