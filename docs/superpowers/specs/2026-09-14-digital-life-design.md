# Digital Life 设计草案

日期：2026-09-14。状态：已确认需求与建议方案汇总，尚未实施。

## 已确认需求

- 个人生活工作台 Web，适配电脑和手机。
- 记录待办、在办、出生天数、固定花销、追番追剧等生活事项。
- 多用户登录，每个账号数据独立。
- 本地开发，代码推送 GitHub，由 CI 执行测试。
- x86 NAS 运行 Docker；通过 `git pull && ./deploy` 更新。
- 参考同级 camera-recorder 项目的工程与部署流程。

## 参考项目的实际情况

已阅读 ../camera-recorder 中的 deploy.sh、docker-compose.yml、
.github/workflows/ci.yml、前后端依赖清单、Dockerfile、Nginx 配置和开发文档。

- 前端 Vue 3、TypeScript、Vite，后端 FastAPI、SQLAlchemy、Alembic、SQLite。
- 前端 Nginx 容器公开 Web 端口，反向代理内部后端服务。
- CI 分为后端测试、前端测试与构建、Docker 构建与启动检查。
- 部署脚本根据上次成功部署版本判断受影响服务；支持检查计划和完整部署。
- 数据和配置保存在 NAS，部署状态在健康检查后记录。

## 建议的工程结构

沿用 Vue 3 + TypeScript + Vite、FastAPI + SQLAlchemy + Alembic + SQLite，
采用 frontend 和 backend 两个服务，便于复用维护经验与分别更新。
前端围绕手机与生活记录设计卡片、列表和表单。

建议目录：

```text
frontend/                  Web、移动布局和 PWA 配置
backend/app/               登录、账号、业务接口和数据模型
backend/tests/             权限和业务测试
backend/migrations/        数据库迁移
.github/workflows/ci.yml   持续集成
docker-compose.yml        NAS 服务编排
deploy                     统一部署入口
scripts/                   部署、备份和恢复辅助工具
.env.example               配置模板
docs/                      开发、部署与恢复文档
data/                      NAS 数据库和用户附件，不入 Git
backups/                   NAS 备份，不入 Git
logs/                      运行与部署日志，不入 Git
```

前后端依赖提交锁文件，CI 和 NAS 构建使用锁定依赖。
NAS 生产目标为 linux/amd64；本地开发保留宿主机原生运行能力。
本地测试使用独立数据目录；Git 不包含真实生活数据、密码或 .env。

## 第一版功能建议

- 今日首页：今日任务、在办事项、出生天数、近期扣费与在看作品。
- 事项：待办、在办、等待中、完成，支持截止日期与备注。
- 人生计时：个人生日、出生天数、自定义纪念日；按个人时区计算日期。
- 固定花销：金额、币种、扣费周期、下一扣费日与停用；月均成本与实际月度应付款分开。
- 追番追剧：想看、在看、看完、搁置，当前集数、总集数与短评。
- 账号设置：个人资料、时区、密码及主题。

日记、照片时间线、自动获取番剧资料、外部提醒和离线编辑作为后续扩展。
第一版先保证核心记录可用，不依赖外部内容平台。

## 账号与数据边界

- 首次部署创建管理员，默认关闭公开注册；管理员可创建和停用账号、重置密码。
- 首次管理员初始化通过受控部署流程执行，不能让任意访客抢先创建管理员。
- 管理员在应用内管理账号；普通业务接口仍只能访问自己的记录。
- 所有业务数据绑定 user_id，由服务端从登录会话确定归属。
- 查询、搜索、统计、详情、修改、删除、导出和附件访问均校验归属。
- 关联记录也必须属于当前用户，不能通过关联 ID 绑定他人的数据。
- 密码只存安全哈希；会话使用 HttpOnly Cookie，写操作包含 CSRF 防护。
- 登出、账号停用和重置密码撤销相关会话。
- SQLite 位于 NAS 本地磁盘；浏览器仅通过 API 访问。
- NAS 管理者具有底层文件访问能力；账号隔离不提供对 NAS 管理者的加密隔离。

## 移动端建议

电脑使用侧栏与多列卡片；手机使用底部导航、单列卡片和统一添加入口。
核心记录流程避免依赖悬停、拖拽或宽表格，所有操作有可点击入口。
PWA 支持添加到主屏幕，正式环境通过 NAS HTTPS 反向代理访问。
第一版需要联网访问 NAS；切换账号时清理前端状态，私人 API 和附件不进入共享离线缓存。

## 开发、CI 与发布

目标流程：本地功能分支开发 → 推送 GitHub → PR CI 通过 → 合并 main → NAS 拉取并部署。

CI 建议覆盖：

1. 后端代码检查、业务测试及双账号越权访问测试。
2. 前端类型检查、核心交互测试与生产构建。
3. 日期边界、月末扣费、金额计算及集数更新边界。
4. Docker Compose 配置检查、amd64 构建、服务启动和经 Web 入口访问 API。
5. 全新数据库初始化，以及旧版本数据迁移后保留记录。
6. 桌面和手机尺寸下的登录、创建待办、变更状态和账号切换流程。
7. 容器重建后数据保留；关键部署失败必须以非零状态退出。

GitHub 仓库尚未配置远程地址。创建或接入仓库后，应将 CI 设置为 main 的合并必要条件；
仅存在 workflow 文件不会自动阻止失败代码进入 main。

## NAS 部署行为

日常入口：

```bash
git pull --ff-only && ./deploy
```

`./deploy` 建议执行：

1. 检查 Docker、Compose、目标架构、配置、端口、数据目录权限和部署锁。
2. 首次生成 .env 和随机密钥；以后保留已有配置与身份信息。
3. 比较当前版本与上次成功部署版本，显示需要更新的服务；支持 `--check-only` 和 `--full`。
4. 构建新镜像；构建失败时保持运行中的服务。
5. 若涉及数据库迁移，暂停写入并制作可恢复的一致性备份，再执行迁移。
6. 更新服务，检查容器健康以及 Web 入口到后端的真实连通性。
7. 全部检查通过后记录成功版本；失败保留日志、备份和上一版本信息。

前端独立更新时保持后端运行；部署不执行 Docker 全局资源清理。
备份必须包含一致的数据库状态，不能直接复制正在写入的 SQLite 主文件。
数据库迁移后的回退需要匹配版本和备份，不承诺通过简单 git 回退自动恢复。
生产数据库和附件均使用持久化挂载，更新不删除数据目录。

## 建议实施顺序

1. 工程与部署基础、登录隔离、账号管理、手机布局和今日首页。
2. 事项、出生天数与纪念日、固定花销、追番追剧。
3. 完成跨模块统计、PWA、备份恢复、端到端检查与 NAS 部署文档。

验收重点：两个账号互不读取或修改记录；手机完成核心操作；同账号多端同步；
CI 可重复通过；NAS 更新成功且数据保留；失败部署给出真实失败状态。
